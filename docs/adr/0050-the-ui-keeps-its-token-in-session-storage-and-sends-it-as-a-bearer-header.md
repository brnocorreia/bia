# The UI keeps its Token in `sessionStorage` and sends it as a bearer header

The UI is a static SPA with no server of its own to hold a session, so the Token a user pastes at login has to live in the browser, and any script running in the page can read whatever the page can. We keep it in `sessionStorage`: it survives a reload, is gone when the tab closes, and is not shared with other tabs or sent automatically with requests, which is the reason we rejected a cookie (it would need a backend to set it and would add CSRF concerns ADR-0043's header-only design avoids). We rejected `localStorage` because it outlives the browser session on a shared machine, for no gain a user would miss, and memory only because every reload would force a new login, which pushes users toward long-lived Tokens pasted from a password manager. All three are equally exposed to XSS, so the real defence is that the UI loads no third-party scripts (assets are bundled, Monaco and React Flow included), renders API strings as text, and is served with a restrictive `Content-Security-Policy` once BIA-29 embeds it; users should sign in with the narrowest Scope that does their job. The login screen verifies the Token with `GET /v1/workflows` before keeping it, and a 401 on any later request clears it and returns to login.
