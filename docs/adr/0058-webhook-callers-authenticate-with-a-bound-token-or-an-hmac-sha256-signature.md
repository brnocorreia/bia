# Webhook callers authenticate with a bound Token or, when the Trigger sets `hmac`, an HMAC-SHA256 signature

How a caller proves it may start a Run from `/hooks/{workflow_id}/{trigger_id}` (ADR-0015) is configured by every sender an operator sets up, so it is fixed here. A webhook Trigger without `hmac` is authenticated by a Token sent as `Authorization: Bearer <token>`: the `webhook` Token bound to that Trigger (ADR-0043), or an `admin` Token; this Token is the Trigger's own secret, revocable and listed like any other, and a `webhook` Token bound elsewhere is refused with `insufficient_scope`. A Trigger with `hmac` is authenticated by its signature instead, because the senders that sign (GitHub, Stripe, Shopify) cannot set an `Authorization` header: the `hmac.header` header must carry the HMAC-SHA256 of the raw request body under the Secret `hmac.secret` names, as lowercase or uppercase hex, optionally prefixed `sha256=` as GitHub's `X-Hub-Signature-256` is, compared in constant time; a missing signature is `missing_signature` and a wrong one `invalid_signature`, both 401, and an unreadable or absent Secret is `hmac_secret_unavailable` (503) so a misconfiguration is not mistaken for a bad sender. A Token sent to an `hmac` Trigger must still be valid for it, so a wrong credential is never silently ignored, but it does not replace the signature: `hmac` is an integrity check the Definition asked for, and a Token cannot vouch for the body. Only SHA-256 is supported; other algorithms and timestamped schemes with replay protection are additive later as fields of `hmac`. To avoid confirming which Workflows exist, a caller that sent no Token gets `missing_token` (401) both for a Trigger that needs one and for a path that names no webhook Trigger of an Active Version, while a caller with a valid Token gets `webhook_not_found` (404); only an `hmac` Trigger reveals that it exists, by asking for its signature. The body is the Run's `input` (JSON, an empty body being `{}`), checked against `input_schema` with `invalid_run_input` (422) before any Run is created, as `trigger_run` does (ADR-0045). The Run's `trigger` is `{ "type": "webhook", "id", "received_at", "headers" }`, where `headers` maps lowercased header names to their values (repeats joined with `, `) minus every header that may carry a credential: `authorization`, `proxy-authorization`, `cookie`, the `hmac.header`, and any header whose name contains `auth`, `token`, `secret`, `signature`, `password`, `session`, `credential`, `cookie` or `key`. A denylist keeps the event and delivery headers that senders put in custom names (`X-GitHub-Event`, `X-GitHub-Delivery`) available to Expressions, and the name rule errs on dropping a header rather than storing a credential. An accepted request answers 202 with `{ "run_id" }` and nothing else about the Workflow, since a webhook caller holds no read access. The handler takes `Option<Webhook>` rather than `Webhook`, the one exception to ADR-0043's rule that a handler's first argument demands a Token, because an `hmac` Trigger may be called without one.
