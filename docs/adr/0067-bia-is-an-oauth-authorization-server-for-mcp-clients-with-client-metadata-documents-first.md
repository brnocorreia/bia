# bia is an OAuth authorization server for MCP clients: Client ID Metadata Documents first, Dynamic Client Registration as a fallback, Grants that tokens belong to

An MCP client pointed at `{public_url}/mcp` signs itself in, following the MCP authorization specification of 2026-07-28, so no one has to hand-make an `agent` Token (ADR-0048). `/mcp` answers an unauthenticated request with 401 and `WWW-Authenticate: Bearer resource_metadata=".../.well-known/oauth-protected-resource/mcp", scope="agent"` (403 `insufficient_scope` for a Token whose Scope is too narrow), and bia serves RFC 9728 and RFC 8414 metadata at the root of `public_url` advertising PKCE `S256`, `authorization_response_iss_parameter_supported`, `client_id_metadata_document_supported` and `scopes_supported: [agent, admin]` (a `public_url` with a path is not supported for discovery). Clients are public: `token_endpoint_auth_method` is `none` and PKCE `S256` is required on every authorization (`plain` and a missing challenge are refused). A `client_id` that is an `https` URL names a Client ID Metadata Document, fetched with an SSRF guard: bia resolves the host itself, refuses the whole answer if any address is loopback, private, link-local, multicast, reserved or an IPv4 address written as IPv6 (mapped, compatible, NAT64, 6to4), connects to the addresses it checked so rebinding cannot swap them, uses no proxy, follows no redirects, reads at most 5 KB, gives up after 5 s and trusts the document for the lifetime its `Cache-Control: max-age` gives, at most 24 hours; the document's `client_id` must equal the URL and its `redirect_uris` are the only ones allowed. The fetcher is an explicit seam, `ApiConfig::client_metadata_fetcher`, which defaults to the strict one and which no configuration touches; the relaxed fetchers tests need (plain HTTP on loopback, a fake resolver) exist only under the `testing` Cargo feature, so a shipped build cannot contain them. Any other `client_id` is a client that registered itself through `POST /oauth/register` (RFC 7591, open, 20 registrations per address per hour counted in memory, marked unverified, redirect URIs `https`, loopback `http` or a native scheme, never `javascript:`, `data:` and the like). Redirect URIs match exactly, except that a registered loopback `http` URI matches any port. `GET /oauth/authorize` shows the person an error instead of redirecting until the client and redirect URI are verified; after that every answer to the client, errors included, carries `iss` (RFC 9207) and `state`. It requires `resource` (RFC 8707) to be `{public_url}` or `{public_url}/mcp` and refuses any other, records a pending authorization server-side for 10 minutes and redirects to `{ui_url}/oauth/consent?request=<id>`; without a `ui_url`, which the CLI leaves unset in a build without the UI unless configured, it answers plain text naming `ui_url`. The consent screen calls `GET /oauth/consent/{id}` and `POST /oauth/consent/{id}/approve|deny`: these need a Session (an `admin` Token of another origin must not approve access for itself), pass the Origin check of ADR-0064, and read the client, redirect URI, resource and requested Scope from the server's record, so the body can only choose a Scope no broader than requested (default `agent`, so an `admin` request can be downgraded) and unknown fields are refused. Approval returns the redirect with a single-use code, valid 60 s, stored as a hash; the code is spent on first presentation whatever else is wrong, and presenting a spent code again revokes the Grant it made. `POST /oauth/token` exchanges it (checking `client_id`, the exact `redirect_uri` and the PKCE verifier) into a Grant, a 1-hour access token and a refresh token. A Grant (client, provenance, Scope, `resource`, User, created, last used, revoked) is the unit a person revokes; its access tokens are ordinary `oauth` Token rows (`grant_id`, `expires_at`, and the Grant's `resource` copied to `audience`), but its refresh tokens live in their own table, so a refresh token can never authenticate a request. Refresh tokens are single-use: each exchange returns a new one, unused ones stop working after 90 days, and a spent one presented again means it leaked, so the Grant and everything it issued is revoked. Audience is enforced where every request is authenticated: a Token whose audience is `{public_url}/mcp` is accepted only through `/mcp` (the MCP server marks the in-process API requests of its tools with a request extension no client can send) and answers 401 `wrong_audience` on `/v1`, while one for `{public_url}` works on both; Tokens with no audience (Sessions, manual Tokens) are unrestricted. `POST /oauth/revoke` revokes the whole Grant for either kind of token, since a client that gives up wants all of it gone, and `GET /v1/grants` and `POST /v1/grants/{id}/revoke` serve the Access screen. `bia serve --reset-admin` revokes Grants and closes open authorizations with the Tokens. The token, revocation and registration endpoints answer in RFC 6749 error format, the rest in the uniform error body; CIMD failures have distinct codes (`client_metadata_blocked`, `_unreachable`, `_too_large`, `_redirected`, `_invalid`, `_mismatch`). Revisit: CIMD domain allow-lists, `client_credentials` and the device flow (BIA-96) are out of scope here; the device flow reuses `client::resolve` and `issue::issue_tokens`.
