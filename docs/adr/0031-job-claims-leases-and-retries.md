# Job claims, Leases and retries: one table, attempt-fenced Leases, notify on enqueue

Every engine path builds on how Jobs are claimed, so these choices are fixed up front. All Job kinds share one `jobs` table, told apart by `kind`; a Worker pool that only takes some kinds (ADR-0006) filters on that column rather than on a table per kind. A claim is one `UPDATE` over a `FOR UPDATE SKIP LOCKED` selection of due Jobs (`run_at <= now`, no live Lease, not given up), oldest `run_at` first, and it increments `attempts`. That counter is the Lease's fencing token: ack, fail and Lease extension all match on `(id, attempts)`, so once a Job is claimed again after its Lease expired, the earlier holder's late calls get `LeaseLost` and its transaction rolls back instead of completing the Job twice. A holder whose Lease expired but whom nobody has replaced may still ack, since the outcome is the same. An expired Lease therefore uses up an Attempt like a failure does, but only an explicit fail gives up: once `attempts` reaches `max_attempts` (set per Job at enqueue, default 20), the Job keeps its row with `failed_at` set and is never claimed again, which leaves it for diagnosis; acked Jobs are deleted. Retry delay is exponential without jitter (`initial · 2^(attempt−1)`, capped), computed from a `Backoff` the caller passes to `fail`, so tests see exact times; claimers already spread out because they poll and wake at different moments. Lease extension is part of the API so long Attempts can heartbeat. An `AFTER INSERT` trigger sends `pg_notify('bia_jobs', kind)`, so every enqueue path wakes listeners and the notification arrives only when the enqueuing transaction commits. Delayed Jobs falling due, expired Leases and retries send nothing, so claimers still claim on a timer and treat notifications as a hint. The `Clock` trait and a manual test Clock live in `bia-core`; the system Clock lives in `bia-store`, because reading the time is IO.
