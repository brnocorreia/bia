# Messages have their own table, Dead-Letter Queues are ordinary Queues, and publishing commits with the Step

Queue and Message storage is hard to change once Messages exist, so these choices are fixed with the first Queues. Messages live in a `messages` table of their own rather than in `jobs`, because a Message is user data with user-facing settings (its Queue's `max_retries`, `visibility_timeout`, `batch_size`, `dead_letter`) and is browsed, kept as a dead letter and retained on its own clock (ADR-0021), none of which a Job needs; the claim machinery is the same as ADR-0031's: a `FOR UPDATE SKIP LOCKED` selection of Messages whose `visible_at` has passed, oldest first, that sets `visible_at` to the end of the visibility timeout and bumps a `deliveries` counter, which fences the delivery's Lease so a consumer whose timeout ran out can no longer ack, retry or extend it. `max_retries` counts deliveries after the first, so a Message is delivered at most `max_retries + 1` times; a failed delivery (nack) waits out an exponential backoff, and one that exhausts its retries, by nack or by its visibility timeout running out, is dead-lettered. A Dead-Letter Queue is an ordinary, explicitly created Queue that another Queue names in `dead_letter` (a foreign key, so it must exist first and cannot be deleted while named); a dead letter moves there as a new row, keeping its body and `published_at` and recording `dead_lettered_from` and `dead_lettered_at`, so no Lease on the old row can touch it, and it starts its deliveries afresh under the Dead-Letter Queue's own settings. A Queue without `dead_letter` keeps its exhausted Messages in place with no `visible_at`, never delivered again, so a failure is never lost. Retention deletes Messages whose `dead_lettered_at` is older than `BIA_DEAD_LETTER_RETENTION_DAYS`, and deleting a Queue deletes its Messages. `queue.publish` and `queue.publish_batch` (at most 100 Messages, each body at most 256 KiB of compact JSON, optional `delay`) are interpreted like the flow Actions (ADR-0035): their Params go through the usual resolution, schema check and Dry Run Mocks, but instead of calling out, the interpreter inserts the Messages in the transaction that records the Attempt, completes the Job and enqueues the next one (ADR-0010). A Message therefore exists exactly when its Step succeeded, and a retried or re-claimed Attempt cannot publish it twice, which is stronger than deduplicating on the Idempotency Key and needs no key column. A missing Queue fails the Step with the `fatal` code `unknown_queue`, and Params that read `secrets.*` fail it with `invalid_params`, because a Message is stored and readable as published. Reusing `jobs` with a `kind` would have shared one claim query, but would have mixed user Messages into engine bookkeeping and forced every Job to carry Queue settings it never uses.
