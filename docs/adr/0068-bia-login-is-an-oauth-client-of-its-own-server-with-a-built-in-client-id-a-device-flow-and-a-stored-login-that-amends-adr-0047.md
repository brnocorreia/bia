# `bia login` is an OAuth client of its own server with a built-in client id and a device flow, and keeps its login in the OS keychain or `credentials.json`, which amends ADR-0047

The CLI signs in through the authorization server of ADR-0067 as `client_id = bia-cli`, a first-party client that `client::resolve` knows without fetching or registration, because a Client ID Metadata Document needs HTTPS and an install may be plain HTTP. Its only redirect URI is `http://127.0.0.1/callback`, which matches any port and nothing else (so it cannot be sent to a non-loopback address, and `bia-cli` is not a URL, so nothing can register or fetch it); the consent screen shows it as "bia CLI (built in)". `bia login` runs authorization code with PKCE `S256` on an ephemeral loopback port, with `resource = {public_url}` (the `issuer` of discovery) and `scope = admin`, checks `state` and `iss`, and opens the browser unless `--no-browser`. `bia login --device` uses RFC 8628 for a machine without a browser: `POST /oauth/device_authorization` (open, only for `bia-cli`, 20 per address per hour in memory, needs `ui_url`) returns a device code (`bia_device_`, 256 random bits, only its SHA-256 stored) and a user code of 8 letters from a 20-letter alphabet without vowels (about 34 bits, shown `XXXX-XXXX`, only its hash stored and unique, so it names one authorization), both valid 10 minutes. The person enters the user code at `{ui_url}/device` and sees the same consent screen; both lookup and answer need a Session like consent does, and a lookup counts against the sign-in throttle of ADR-0064 so guesses slow down. The CLI polls `POST /oauth/token` with grant type `urn:ietf:params:oauth:grant-type:device_code` no sooner than the server's `interval` (5 s); the server answers `authorization_pending`, `slow_down` (and adds 5 s to the interval for that code), `expired_token` and `access_denied` as the RFC says, from the injected `Clock`. An approved device code is spent when it first returns tokens, in the transaction that creates the Grant, and presenting it again revokes that Grant. The stored login (access token, refresh token, expiry, Scope) is keyed by the server URL: in the OS keychain through `keyring` when it works, else in `credentials.json` in `$BIA_CONFIG_DIR`, `$XDG_CONFIG_HOME/bia` or `~/.config/bia`, written with mode 0600 in a 0700 directory. This amends ADR-0047's "no implicit file" rule for that one location, and only `login` writes it; `BIA_KEYCHAIN=off` skips the keychain, which is what tests use. Precedence is `BIA_TOKEN` or the config file's `token`, then a stored login, and the Token still has no flag. Commands and `bia mcp` send the stored access token, renew it when it is within a minute of expiring, and on a 401 renew and retry once; because a refresh token is single-use and a reused one revokes the Grant, renewal takes a file lock and re-reads the login, so concurrent `bia` processes share one refresh. A refresh that fails with `invalid_grant` deletes the stored login, so the 401's hint says to run `bia login`. `bia logout` revokes the Grant through `/oauth/revoke` and deletes the stored login even if the revoke fails (and then exits 1 saying so). `keyring` was chosen as the mainstream cross-platform keychain crate; its Linux backend pulls `zbus` 5, whose three helper crates carry unmaintained notices that `deny.toml` ignores until `keyring` moves to `zbus` 6.
