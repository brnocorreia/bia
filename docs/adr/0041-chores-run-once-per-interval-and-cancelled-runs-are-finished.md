# Chores run once per interval from a row in Postgres, and cancelled Runs count as finished for retention

Run retention (ADR-0021) runs as a Chore on the leading scheduler, and it must run once per interval with any number of schedulers, while ADR-0039 only kept a Chore's next run in the leader's memory, restarted on each new leader and so run early, or twice while two schedulers briefly both lead. A `chores` row now records when each Chore last ran, keyed by its stable name, and the scheduler claims a run with one upsert that sets `ran_at` to the Clock's now only when the stored `ran_at` is at least one interval old; concurrent claimers queue on the row and the later ones see the new `ran_at`, so exactly one wins each interval, and a new leader waits out the interval its predecessor started. The claim commits before the Chore's work, so a Chore that fails or is cut short waits for its next interval rather than retrying at once, which retention tolerates because it resumes from whatever is left. Retention deletes in batches of 500 Runs per transaction, up to 20 batches per retention kind per run, every 10 minutes, so a backlog clears over several runs without holding up cron Triggers. Cancelled Runs follow `BIA_RUN_RETENTION_DAYS` with succeeded ones, because cancelling is an operator's decision rather than a failure to investigate; only `failed` Runs follow `BIA_RUN_FAILED_RETENTION_DAYS`. Dead-Letter Queue contents follow `BIA_DEAD_LETTER_RETENTION_DAYS`, all three defaulting to 90.
