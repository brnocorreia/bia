# Passkeys are an alternative to the password, with the RP ID from `public_url`, ceremony state in Postgres and a ten-minute reauthentication window

Passkeys (`webauthn-rs` 0.6, which is pure Rust and brings no OpenSSL, so CI and release builds need no system library) are another way to start the same Session ADR-0064 defines, not a second factor and not a way to have no password: the password stays required to set up and to recover, so `--reset-admin` still has one way back. A `passkeys` table holds `user_id`, a name and the serialised credential as `jsonb` (public key and signature counter, opaque to `bia-store`), and `bia serve --reset-admin` deletes the rows. The relying party is derived from `public_url`: its host is the RP ID and the allowed origins are `public_url`'s and `ui_url`'s, with no subdomains, so a response made on any other origin or for another RP ID fails verification and a `public_url` whose host is an IP address answers `passkeys_unavailable` (409); `ui_url` is allowed because a UI on another port of the same host (development, the end-to-end tests) is a legitimate place to run the ceremony, but a UI on another host than `public_url`'s cannot use passkeys, since the browser refuses an RP ID that is not the page's host or a parent of it, until a later decision widens this. The challenge state of each ceremony lives in a `passkey_ceremonies` table (`begin` inserts, `finish` deletes and returns the row once), valid for five minutes judged against the injected `Clock` (ADR-0022), rather than in memory: unlike the throttle, a lost entry here breaks a sign-in half way, and several API processes would otherwise need sticky routing; this is why `webauthn-rs` is built with `danger-allow-state-serialisation`, and the stored state never outlives its ceremony (unfinished rows are deleted by the next `begin`). Sign-in `finish` counts as an attempt in the ADR-0064 throttle before anything is checked and clears it on success, so a failed passkey and a wrong password share one count, while `begin` is free. Removing a passkey needs a Session whose `created_at` (the sign-in) is under 10 minutes before `now`, else 403 `reauthentication_required`; a Token that is not a Session cannot show a sign-in and is refused the same way, so a stolen, long-lived Session or Token cannot strip the account's passkeys. Registering needs no such window, since adding a way in is what a signed-in admin is entitled to do. Both `webauthn-rs` and its `crypto-glue` dependency are MPL-2.0 (file-level copyleft, unmodified), so `deny.toml` allows MPL-2.0 for those crates only, and ignores RUSTSEC-2023-0071 (`rsa` Marvin attack, no fix exists) because bia only verifies passkey signatures with public keys, never decrypting or signing with an RSA key. We rejected keeping the challenge state in memory.
