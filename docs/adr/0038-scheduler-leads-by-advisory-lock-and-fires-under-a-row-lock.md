# The scheduler leads by advisory lock, fires under a row lock, and rebuilds Schedules from the Active Version

Several scheduler replicas may run (ADR-0005), and a cron occurrence must start exactly one Run. Each replica polls on its Clock (1s by default) and tries a session-level `pg_try_advisory_lock` on a connection of its own, outside the pool, because a session lock stays with its connection and a pooled one would carry it back into the pool; when the leader's process dies or its connection drops, Postgres frees the lock and the next replica to poll takes over, and a leader that stops on SIGTERM unlocks at once. Leadership only saves work, because a leader whose connection dropped can believe it still leads until its next poll. Exactness comes from firing: one transaction claims a due Schedule row with `FOR UPDATE SKIP LOCKED`, shares the Workflow row lock while requiring the Schedule's Version to be the Active Version, creates the Run and its first Job (ADR-0010), and writes the Schedule's next occurrence back, so two firers can never both see the same occurrence due, and a Version that stops being active cannot fire after the change commits. Schedules are materialised state, one row per cron Trigger of an Active Version, rebuilt by the scheduler rather than by whoever changes the Active Version: `workflows.scheduled_version` records which Version the rows were built from, and every poll rebuilds the Workflows where it differs from `active_version`, under that Workflow's row lock. Every path that changes the Active Version, today's repository and later the API, is then covered without knowing about Schedules, at the cost of up to one poll before a new Version's Triggers exist. A rebuilt Trigger keeps its next occurrence and queue when its `expr`, `tz` and `jitter` did not change, and always keeps the Run it started last, so `overlap: skip` still sees a Run the previous Version started. Periodic upkeep such as retention (ADR-0021) runs as a Chore on the leader, on an in-memory interval restarted on each new leader, so a Chore must tolerate running early or twice.

## Considered Options

- Leadership alone for exactness: rejected. A leader cut off from Postgres cannot know it lost the lock until it next talks to it, so two leaders overlap briefly.
- Firing through a Job a Worker claims: rejected for now. It adds a hop and a Job kind for work the scheduler finishes in one short transaction.
- Rebuilding Schedules inside the activation transaction: rejected. It needs every activation path to compute cron occurrences, and nothing would repair Schedules written by a path that forgot.
