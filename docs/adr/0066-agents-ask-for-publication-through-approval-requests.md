# Agents ask for publication through Approval Requests, which an admin approves into a publish and activate in one transaction

This amends ADR-0008 (an `agent` still cannot publish or activate, but may ask a human to) and ADR-0048 (three new tools). `POST /v1/approval-requests` takes `{workflow_id, number, action, note}` from an `agent` or `admin` Token, where `action` is `publish`, `publish_and_activate` or `activate`, and stores a row in `approval_requests` with the requesting Token and its User. A Draft target must pass publishing's checks (the `publish` validation target) or the call fails with `invalid_definition` and creates nothing, and the request records the SHA-256 of the Draft's canonical Definition; `activate` needs a Published Version and records no hash. One request per Workflow may be `pending`, enforced by a partial unique index, so a new request marks the old one `withdrawn` in the same transaction. `approve` and `reject` need `admin` and take an optional `comment`. Approving runs, in one transaction, the same validate-and-publish as `POST .../publish`, the activation, and the status change with the deciding User, so a failing publish (say a Queue deleted since the request) rolls everything back and the request stays `pending`; it also refuses with `version_changed` when the published content's hash is not the recorded one. Replacing a Draft marks its pending request `stale` in the replace's transaction, so an admin never approves content they did not see, and `stale`, decided and withdrawn requests answer 409 `approval_request_not_pending` to every decision. Lock order is Version row before request row on both paths (publish then decide, replace then stale), so the two cannot deadlock. There is no expiry and no notification. The MCP tools `request_approval`, `get_approval_request` and `withdraw_approval_request` each map to one endpoint; there is deliberately no tool to approve or reject, and their descriptions tell the agent to use `request_approval` instead of asking a human to publish. Responses carry the requesting Token's name (`requester_name`), so a review page needs no second call.
