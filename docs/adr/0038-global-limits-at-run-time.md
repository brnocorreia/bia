# Global limits are enforced at run time as `fatal`, coded failures, and a Definition can only lower them

ADR-0012 names four configurable global limits; validation rejects what breaks them statically, and the interpreter enforces what only a running Run knows. `max_steps_per_run` (default 10,000) counts Steps, not Attempts: a Step counts once each time the Run reaches it, whatever it ends as (`succeeded`, `failed`, `skipped`, a Block choosing an arm), and each loop iteration counts again, while retries and waking from a sleep do not, because retries are already bounded by the Step's `retry` policy and counting them would let a flaky upstream fail an otherwise bounded Run. The count lives in the Checkpoint (`steps`), so it survives Jobs and crashes. `max_output_bytes` (default 256 KiB) measures an Output as its compact JSON serialisation, the form it is stored and read in; a larger Output fails its Step and is never written to the Timeline or the Checkpoint. `max_iterations` (default 10,000, the same as validation's) and `max_subworkflow_depth` (default 8; a Run no Subworkflow started is depth 0) are checked through `RunLimits::check_iterations` and `RunLimits::check_subworkflow_depth`, which the loop and Subworkflow Blocks call. Every breach is a `fatal` error, so it never consumes retries, with its own Timeline code (`run_step_limit_exceeded`, `iteration_limit_exceeded`, `subworkflow_depth_exceeded`, `output_limit_exceeded`) and `details` naming the limit, its value and what went past it; the step code is not `step_limit_exceeded` because that Diagnostic already means a Definition declares too many Steps. A Definition's `limits` (`max_steps_per_run`, `max_output_bytes`) and a loop's `max_iterations` can only lower the global limit, and a higher value is capped at it, because the global limits are the operator's protection against any one Workflow, which an author or agent must not be able to opt out of.
