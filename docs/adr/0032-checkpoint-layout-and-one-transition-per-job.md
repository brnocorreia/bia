# Checkpoint layout: Cursors are Step pointers, and each Job makes one transition

A Run's Checkpoint is read back by every later build, so its layout is hard to change once Runs exist. The Cursor is the JSON Pointer path to the Step the Run executes next, stored as segments (`["steps", 2]`); Blocks will extend it with the nested list and position (`["steps", 2, "then", 0]`), so a Cursor names the same Step an author sees in Diagnostics. A pending or succeeded Run has an empty Cursor, and a failed Run keeps its Cursor on the failed Step, so it can later be resumed from there (ADR-0012). The rest of the Checkpoint is `{ "outputs": { "<step_id>": <Output> }, "attempts": n }`: the Outputs Expressions read as `steps.<id>.output` (ADR-0011), and how many Attempts the Step at the Cursor has finished, which numbers the next Attempt and decides when its `retry` policy is used up. Each `advance_run` Job makes exactly one transition (start the Run, or one Attempt of one Step) and commits it with its own completion and the next Job (ADR-0010); a retry is that next Job delayed by the backoff, not a failed Job, so Job-level retries stay reserved for the engine failing. Starting a Run is its own transition, so input that breaks the `input_schema` fails the Run before any Step runs. The Idempotency Key is always the three parts `run_id:step_id:iteration_path`, joined by `:` even when the iteration path is empty outside loops (`<run>:send:`), so it splits the same way everywhere. The defaults the DSL leaves open are a 5-minute Attempt timeout and `exponential` backoff from `1s` up to `1h`.

## Amendments

- The Checkpoint also holds `"steps": n`, how many Steps the Run has taken up, which `max_steps_per_run` counts (ADR-0038). A Checkpoint written before it reads as 0.
