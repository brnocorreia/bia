# Run routes, the Timeline entry and what resume and retry do

Runs are driven by agents, so the contract is fixed here. `POST /v1/workflows/{id}/runs` (`trigger_run`) takes `{ input?, trigger_id? }` and starts a Run on the Active Version from a manual Trigger (the first one unless `trigger_id` names another); it refuses with `no_active_version` or `no_manual_trigger` (409), and checks the input against the Version's `input_schema` before creating anything, answering `invalid_run_input` (422) with the violations in the message: failing fast beats leaving a failed Run behind, and the interpreter keeps its own check for Triggers that do not go through this route. `GET /v1/runs` (`list_runs`) filters by `workflow_id`, `status`, `created_from` (inclusive) and `created_to` (exclusive), newest first, and pages with keyset pagination: `limit` (1 to 200, default 50) and `after`, answered by `next_after`, which is absent on the last page and stays correct while Runs arrive, unlike offsets. `GET /v1/runs/failures` (`list_failures`) is the same list restricted to `failed` Runs with the last failed Timeline entry inlined; `GET /v1/runs/{id}` (`get_run`) returns the Run, its input and its Timeline; `POST /v1/runs/{id}/cancel` answers 202 because a Worker ends the Run a moment later (`run_finished` if it already ended); `.../resume` and `.../retry` are below. All of them need only the `agent` Scope. A Timeline entry is flat JSON: `seq`, `step_id`, `iteration_path`, `attempt`, `action` (all absent for an entry about the Run as a whole), `status` (`succeeded`, `failed`, `skipped`, `cancelled`), `input`, `output`, `error` (ADR-0033), `started_at`, `finished_at` and `duration_ms`; a Run's `timeline` is the array of them ordered by `seq`, and Dry Run returns the same entries so agents read both alike. Resume (`resume_run`) accepts only a `failed` Run whose Cursor rests on a Step (else `run_not_resumable`), flips it back to `running` on its own Version and enqueues a Job in one transaction; the failed Step is retried with a fresh retry budget while Attempt numbers keep counting up (the Checkpoint records the Attempts before the resume), so the Timeline stays one monotonic story and the Idempotency Key stays the same. Retry (`retry_run`) accepts any finished Run and starts a new Run on the original's Version with its input; its `trigger` is the original's plus `retry_of`, so Expressions reading `trigger` still work and `retry_of` is surfaced on the Run. Retrying on a newer Version means triggering the Workflow again.
