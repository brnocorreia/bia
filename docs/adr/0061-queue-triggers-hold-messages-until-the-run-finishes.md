# Queue Triggers hold their Messages until the Run finishes, which settles them

When a Message dispatched to a Run counts as done is user-visible delivery semantics, so it is fixed with the first queue Trigger. The scheduler dispatches, like it fires Schedules (ADR-0039): it materialises one `queue_triggers` row per queue Trigger of an Active Version when it rebuilds a Workflow's Schedules. On every poll, the leader dispatches for each Trigger whose Queue has a claimable Message. Each dispatch is one transaction. It shares the Workflow row lock while requiring the Trigger's Version to be the Active Version, claims up to `batch_size` Messages with ADR-0059's `SKIP LOCKED` claim, creates the Run with its first Job, and records the Run on those Messages (`messages.run_id`). There is no batching window: a Run takes what is claimable, up to `batch_size`, and Triggers take turns one batch at a time so one backlog cannot starve another consumer of the same Queue. Acks follow the Run, not the dispatch. While `run_id` is set, the Message is held: no claim takes it, its visibility timeout does not run, and the claim's Lease can no longer ack, retry or extend it. So a Run that sleeps for days never shares its Messages with another Run, and nothing has to heartbeat on its behalf. The transition that finishes the Run settles its Messages in the same transaction that writes the final Checkpoint (ADR-0010). Success deletes them. Failure gives each one back after an exponential backoff (1s doubling, capped at 1h), or dead-letters it once it has used its Queue's `max_retries`, so a batch that keeps failing ends up as dead letters. Cancellation dead-letters them at once, because an operator who stopped the work wants it neither redone nor lost. A failed Run that is resumed or retried holds nothing, since its Messages already went back to the Queue. Acking at dispatch (at most once per Run) was rejected because a crash or failure would lose Messages that never got processed. Keeping the ordinary visibility timeout and extending it while the Run lives was rejected because a sleeping or waiting Run has no process to extend it, and a missed extension would put a Message in two Runs at once. A future `max_concurrent_runs` (BIA-44) can hold dispatch back the same way it holds cron firings.
