# Dead letters are replayed as new Messages in their source Queue, and replay and purge take a bounded selection

Operators recover dead letters from the UI (and the API) by replaying or purging them, and the endpoint shapes and replay semantics are a public contract that is hard to change later. `POST /v1/queues/{name}/dead-letters/replay` and `POST /v1/queues/{name}/dead-letters/purge` are admin-only and take `{ "ids": [...] }` naming 1 to 200 dead letters of that Queue (a page of `GET .../messages`), so each runs as one short transaction rather than an unbounded sweep; ids that are not dead letters of the Queue are skipped rather than failing the batch, and the response says what was done (`replayed` new ids, `purged` count). A replayed dead letter is deleted and re-inserted, in the same transaction, as a new Message in the Queue named by its `dead_lettered_from` (its own Queue when it was kept in place), visible from now, with `deliveries` back at 0, its body, `published_at` and `last_error` kept and its dead-letter fields cleared: the source Queue's `max_retries` applies afresh, which is what an operator who fixed the cause expects, and the new row means no Lease held on the old one can ack or retry it, exactly as dead-lettering moves a Message (ADR-0059). Dead letters a consumer holds within its visibility timeout are skipped, since replaying them would deliver them twice, and so are those whose source Queue was deleted. Queue responses carry `messages` counts (`ready`, `in_flight`, `delayed`, `dead_lettered`) that partition a Queue's Messages, a dead letter counting only as `dead_lettered` even in a Dead-Letter Queue whose consumers still receive it.
