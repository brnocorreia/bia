# Store table layout: natural Workflow keys, per-Workflow counters and structured Cursors

Table layout is hard to change once data exists, so the first migration fixes these choices. Workflows are keyed by their natural id (`onboarding-email`), which every Definition already carries, and Versions by `(workflow_id, number)`; the Active Version is a nullable `active_version` column on `workflows` with a foreign key to that pair. Version numbers come from a `last_version` counter on the Workflow row, bumped with `UPDATE … RETURNING`, so concurrent saves serialise on that row and numbers stay gap-free 1, 2, 3…. A Version's state is `draft` or `published`, and a trigger rejects any update to a Published row, so immutability holds even for SQL the repositories do not write; how many Drafts a Workflow may hold at once is left to the API (BIA-21). Definitions, Run inputs, Checkpoints, Params, Outputs and errors are `jsonb`. Runs get a database-generated UUID. The Cursor sits in its own `jsonb` column as an array of path segments through nested Blocks, separate from the rest of the Checkpoint, so it can be read without decoding Checkpoint state; the interpreter (BIA-12) owns the segment vocabulary. Timeline entries are one row per Attempt, ordered by a per-Run `seq` taken from a `timeline_len` counter on the Run row, which gives each Run a gap-free order even when parallel branches append concurrently. Statuses are `text` with `CHECK` constraints rather than Postgres enums, which keeps them plain strings in `sqlx` and lets later migrations widen them by swapping a constraint. Every behavioural timestamp (Run creation and transitions, Attempt start and finish, publish time, when a Job becomes claimable) is a parameter supplied from the `Clock` (ADR-0022); only `created_at` audit columns on Workflows, Versions and Jobs default to `now()`.
