# Blocks nest in the Cursor, and the flow Actions that act on the Run are interpreted

A Cursor is a path of `[list, index]` pairs, one per level of Block (`["steps", 1, "then", 0]`), and the interpreter moves it with two generic operations: entering a Block's nested list, and, when a list is used up, leaving the Block and continuing in the parent list, so later Blocks only have to say which nested lists they have. `flow.branch` records its own Timeline entry and Output `{ "arm": "then" | "else" }` when it chooses an arm, and an empty arm falls through to the Step after the Block. `flow.sleep`, `flow.sleep_until`, `flow.fail` and `flow.succeed` are registered like any Action so validation and the catalogue know them, but the interpreter executes them itself because they change the Run: a sleep leaves the Cursor on its Step, sets the Run `sleeping` and enqueues the next Job delayed until the wake time (no Job is claimable and no Lease held meanwhile; the wake time lives in the Checkpoint and the Timeline entry is written on waking), `flow.fail` fails the Run with a `fatal` error coded `flow_fail`, and `flow.succeed` ends the whole Run as `succeeded` from whatever depth it sits at. Their Params are resolved without Secrets, so no message or Output can carry one. `if` and `when` that do not evaluate to a boolean fail the Step with the new code `invalid_expression`. A later `flow.try` or `on_error` decides what a caught failure does; `flow.succeed` is not an error and is never caught.
