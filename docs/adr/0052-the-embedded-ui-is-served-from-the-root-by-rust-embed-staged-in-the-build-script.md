# The embedded UI is served from the root by `rust-embed`, staged by the build script

BIA-29 embeds the UI behind `bia-server`'s `ui` feature. It is mounted at `/`, not `/ui`: the bundle uses absolute asset paths and reads `/config.json` from the site root (ADR-0051), so a sub-path would need a build-time base or a rewriting server, and the same build would no longer deploy unchanged to Pages or CloudFront; the API's names (`/v1`, `/mcp`, `/health`, `/ready`, `/openapi.json`) are fixed and the UI's screens never need them. The UI is the router's fallback, so it only answers what no API route matched, answers only `GET` and `HEAD`, leaves `/v1` and `/mcp` to the uniform error body, and turns a missing path with a file extension into a 404 instead of `index.html`; any other path gets `index.html` for client-side routing. It serves a generated `config.json` of `{"apiUrl":""}` (same origin) rather than the bundle's. We chose `rust-embed` over `include_dir` for content types and content hashes (used as `ETag`s) without extra code. The build script copies `ui/dist` into `OUT_DIR` and embeds that copy, so the binary matches the bundle and is rebuilt when it changes; a build without the feature never looks at `ui/dist` or needs Node. When `ui/dist` is missing, debug builds embed a placeholder page so `cargo clippy|test --all-features` work on a fresh checkout, and release builds fail, so a shipped binary cannot silently lack its UI. Responses carry a `Content-Security-Policy` allowing only the bundle's own origin (ADR-0050); hashed `assets/` are cached immutably and everything else revalidates.
